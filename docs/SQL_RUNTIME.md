# SQL-среда: исполнение, лимиты и восстановление

Дата: 2026-11-12. Реализация: `src/sql-client.js`, `src/sql-worker.js`, подключение в `src/app.js`; проверка результата остаётся в `src/sql.js`.

## Что изменилось

Раньше `initDatabase()` создавал PGlite непосредственно в `app.js`, а `await db.query()` запускал синхронные вычисления PostgreSQL/WASM в потоке интерфейса. `queryReadOnly()` обеспечивал читающую транзакцию и очередь, но не ограничивал время или объём результата. Пример для воспроизведения исходного риска: `SELECT COUNT(*) FROM generate_series(1,1000000) a CROSS JOIN generate_series(1,1000000) b` мог надолго заблокировать страницу.

Теперь обе учебные базы создаются внутри одного модульного Web Worker. Основной поток получает только сообщения с клонированными результатами. Даже при занятом SQL-потоке навигация и таймер остановки остаются доступны. Браузер загружает закреплённую версию PGlite 0.5.15 из сборки `vendor/pglite`, без исполнения JavaScript со стороннего CDN.

## Фактические ограничения

| Объект | Правило |
| --- | --- |
| SQL | Один `SELECT` либо `WITH … SELECT`, до 20 000 символов. Проверяется на обеих сторонах RPC. |
| Изменение данных | `BEGIN TRANSACTION READ ONLY`, обязательный `ROLLBACK` после выполнения, включая ошибки. Изменяющие CTE отклоняет PostgreSQL. |
| Число строк | Курсор PostgreSQL получает не более 1001 строки. Больше 1000 — явная ошибка с просьбой ограничить результат. Усечённый ответ не выдаётся за полный и не может пройти проверку. |
| Размер ответа | Не более 1 000 000 символов сериализованного JSON. Это ограничение перед отправкой результата, **не** жёсткая квота памяти процесса. |
| Время запроса | 8 секунд после отправки запроса worker. |
| Проверка решения | 20 секунд на всю проверку результатов в основной и изменённой базе. |
| Инициализация | 90 секунд для загрузки WASM и двух баз. |
| PostgreSQL | `work_mem=8MB`, `temp_file_limit=16MB` в читающей транзакции. Эти настройки не ограничивают весь объём памяти WASM. |

RPC выполняются последовательно. Время ожидания предыдущей операции не вычитается из лимита следующей. При превышении времени worker принудительно завершается целиком; непроверенный запрос не переигрывается. Создаётся новый worker, заново загружаются исходные данные обеих баз. Прогресс и черновики живут отдельно и сохраняются. Синтаксическая ошибка или превышение размера результата завершают текущую транзакцию без необходимости пересоздавать базы.

## Границы безопасности

Это локальная среда для самостоятельного обучения. В ней нет сервера с данными других пользователей, сетевых учётных данных или общего изменяемого PostgreSQL. Исходные данные, контрольный набор и эталоны доступны в публичных исходниках; скрытыми экзаменационными тестами они не являются. Локальный прогресс можно изменить вручную, поэтому он не является основанием для защищённого сертификата.

Web Worker изолирует исполнение от потока интерфейса и позволяет принудительную остановку, но не обеспечивает ОС-квоту памяти: запрос с очень крупным отдельным значением может занять память ещё до проверки размера ответа. Для недоверенной многопользовательской серверной песочницы нужны отдельные процессы/контейнеры, роли, квоты памяти/CPU, сетевые ограничения и серверная проверка. Такую среду этот релиз не имитирует.

PGlite действительно выполняет PostgreSQL-запросы, включая CTE, оконные функции и JSON. Это не полноценный многосессионный сервер: лабораторные по конкурирующим транзакциям, изоляции, блокировкам, репликации, параллельным серверным планам и администрированию должны выполняться в отдельной PostgreSQL-среде с документированной настройкой. Текущий редактор принимает только читающие запросы; DDL/DML и административные упражнения не объявляются доступными.

## Проверки

`tests/runtime.test.mjs`: принудительное завершение и восстановление worker без повтора тяжёлого запроса; очередь запросов; отклонение слишком большого и многооператорного SQL; реальный PostgreSQL-курсор с NULL, дубликатами и сортировкой; отклонение избыточного результата; запрет изменяющего CTE; восстановление читающей транзакции после ошибки; принятие эквивалентного CTE-решения.

Браузерные проверки настоящего worker, мобильной навигации и опубликованной версии фиксируются в `PROJECT_STATUS.md`; наличие этого документа само по себе не означает прохождение браузерного теста.
