# UX и доступность: аудит исходников

Дата: 12 ноября 2026. Основание: локальный снимок исходников `83a6dae` (upstream `95b4f3f`) и рабочее дерево с исправлениями текущей итерации. Файлы активно изменяются; номера строк относятся к моменту чтения, устойчивые ориентиры — имена функций и CSS-селекторы.

## Область и метод

Прочитаны весь `index.html`, весь `styles.css`, все функции представлений `src/views.js` и связанные обработчики `src/app.js`, модель прогресса `src/progress.js`. Проверены источники навигации, мобильных перестроений, форм редактора, таблиц, тем, уведомлений и отображения учебных достижений. Контраст выбранных явно заданных пар рассчитан по формуле относительной яркости sRGB WCAG.

Это **исходниковый и сценарный аудит**. Он не подтверждает реальную работу со скринридером, качество мобильной клавиатуры, соответствие WCAG 2.2 AA целиком или удобство для реальных студентов. Автор этого исходникового отчёта не запускал axe SQL4LEARN; основной агент разработки провёл отдельные браузерные проверки и сообщил результаты ниже. Реальное пользовательское исследование не проводилось.

## Исторические находки и оставшиеся рекомендации

### UX-01. Перерисовка внутри страницы уничтожает фокус

**Первичная находка высокого приоритета; исправлена в текущем diff.** `app.js`, `render` (`#app.innerHTML=...`) заменяет всё содержимое main. Обработчики схемы, фильтра, выбора задачи, ответа на квиз и отметки чтения вызывают эту функцию с `keepScroll:true`. До исправления сохранялась только позиция прокрутки, без DOM-узла, курсора или фокуса. Обновления состояния SQL-движка тоже перерисовывают main.

Воспроизводимый сценарий для проверки: открыть урок → Tab до выбора другой задачи → Enter → следующий Tab. Ожидание: логичное продолжение рядом с выбранной задачей/редактором; исходники не содержат механизма восстановления фокуса для этого сценария. Отдельно проверить ответ на квиз и смену таблицы схемы. Исправление фокуса при `hashchange` этой проблемы не покрывает.

Решение: адресно обновлять изменившуюся панель либо сохранять устойчивый ключ активного элемента и восстанавливать фокус после rerender. При выборе новой задачи уместно фокусировать её заголовок/редактор по объявленной последовательности. Не перемещать фокус при каждом фоновом статусе движка. Связанные требования: WCAG 2.4.3, 3.2.2; нарушение не объявляется подтверждённым без сценарного теста.

### UX-02. Открываемое мобильное меню не управляет фокусом

**Первичная находка высокого приоритета; перенос/возврат фокуса исправлен.** `index.html`: sidebar находится раньше topbar и `#menu-toggle` в DOM. В исходном `app.js`, `toggleMenu`: только класс open, aria-expanded, backdrop и закрытие по Escape/навигации. Не было перемещения фокуса в открывшуюся навигацию и возврата на кнопку при закрытии.

Проверка на ≤760px: сфокусировать кнопку меню → Enter → Tab. Так как ссылки располагаются перед кнопкой, стандартный Tab идёт дальше по topbar, а не в появившееся меню. При закрытии Escape с фокусом внутри скрывающегося sidebar фокус может оказаться на невидимом узле.

Нужно выбрать ясную модель: для модального drawer — фокус внутри, возврат на trigger и недоступный фон; для немодального раскрытия — предсказуемая последовательность и возможность сразу перейти к ссылкам. Backdrop сам по себе не создаёт модальный диалог. Наличие Escape и aria-expanded — полезная основа, но не полная реализация.

### UX-03. Выбранные состояния в основном представлены только классами

**Первичная находка среднего/высокого приоритета; aria-pressed добавлен в `app.js`, `render`.** `views.js`: `quiz` (примерно 120), `schemaPanel` (199), выборы задач (223/253/345), фильтры (242), X-Ray (381/384). Исходные кнопки использовали только active/correct/wrong. Основная навигация уже выставляла `aria-current=page` (`app.js`, `updateNav`).

Поддержать доступное состояние выбранной схемы/фильтра, а для взаимоисключающего ответа — native radio или согласованный доступный виджет. Слово «вкладка» и CSS-класс tab не обязывают использовать ARIA tabs: если этот паттерн выбирается, нужны tablist/tab/tabpanel, связь панелей и клавиши стрелок; простая группа кнопок с aria-pressed тоже допустима. Не добавлять роль без соответствующего поведения.

### UX-04. Объявления результатов не единообразны

**Средний приоритет; атрибуты live region добавлены, проверка AT остаётся.** Изначально `renderPlayground` (`views.js:372`) создавал `#task-feedback` без live region; `renderXray` (`#xray-result`, около 390) тоже не объявлял появление результата. Теперь оба содержат role=status/aria-live=polite. Квиз даёт текстовое «Верно»/«Есть ошибка», но полностью заменяется render. Наличие текстового сообщения и сохранение фокуса не доказывают получение нового сообщения AT.

Оставить стабильную краткую live region со статусом, а не читать целиком большую таблицу. Саму таблицу предоставить как отдельную доступную область. После проверки SQL сохранить фокус в рабочем контексте. Связанные требования: 4.1.3 и 4.1.2; нужен тест со скринридером.

### UX-05. Отдельные пары контраста остаются рискованными

**Первичная находка высокого приоритета; перечисленные пары исправлены.** В исходном `styles.css:4` в dark `--blue:#8393ff`, а `.btn.primary` задавал белый текст. Контраст этой пары — **2.77:1**, при размере 12px требуется 4.5:1. Для исходной `.sidebar-section` цвет `#7180a1` на `#101a34` давал **4.35:1**, размер 10px тоже не относится к крупному тексту. Текущие overrides меняют цвета текста этих компонентов; старые коэффициенты к ним уже не относятся.

Светлые muted/teal после исправления проходят для рассчитанных пар. Контраст нужно проверять по вычисленным стилям всех основных состояний, а не по одной переменной. Для dark primary подходит отдельный цвет текста или отдельная более тёмная заливка кнопки. Локальные вычисления не заменяют браузерный axe и проверку фокуса/иконок.

### UX-06. На телефоне схема уходит после большого блока урока

**Средний приоритет.** `styles.css:12`: ≤1040px workspace становится одной колонкой; ≤760px правая область тоже одна колонка. DOM в `renderLesson` ставит aside со схемой после теории, квиза, практики и навигации. На большой странице новичку приходится далеко прокручивать между редактором и схемой. В независимом проекте инструкция «в правой колонке» (`views.js:341`) не соответствует одноколоночному виду.

Есть хорошие элементы адаптации: min-width:0 у рабочих колонок, локальная горизонтальная прокрутка результата, вертикальное изменение размера textarea, перенос кнопок. Но мобильный рабочий процесс пока в основном получается перестроением сетки; переключения «Задача / Схема / SQL / Результат» или прямого перехода к схеме рядом с редактором нет.

Нужна проверка с открытой экранной клавиатурой: доступность Run/Check, сохранение строки курсора, горизонтальная прокрутка SQL отдельно от страницы, возвращение к условию. Это приоритет развития UX, а не доказанная невозможность учиться с телефона.

### UX-07. Прокрутка к разделу не переносит клавиатурный контекст

**Средний приоритет.** `views.js`, `lesson-tools` содержит кнопки «Объяснение», «Понимание», «Практика». `app.js`, `onClick`, `data-scroll` вызывает только `scrollIntoView({behavior:'smooth'})`. Фокус остаётся на кнопке наверху; следующий Tab продолжает обход с прежнего места. Sticky topbar может перекрывать начало прокрученного раздела, поскольку для целевых sections не задан `scroll-margin-top`.

Проверить: Tab до «Практика» → Enter → Tab. Желательно вести к целевому заголовку/редактору с сохранением понятного фокуса и учитывать высоту шапки. Поскольку это переходы внутри страницы, их можно представить якорными ссылками с обработкой маршрутизатора либо реализовать доступное фокусирование явно. CSS reduced-motion уже есть, но явный JavaScript `behavior:'smooth'` нуждается в отдельном учёте предпочтения пользователя.

### UX-08. Метрики завершения не полностью совпадают с формулировками освоения

**Средний продуктовый приоритет.** `views.js:21`, `lessonDone`: все SQL-задачи (либо сохранённый исторический зачёт) + правильный ответ квиза. `read` не проверяется. На главной при этом указано «Уроков освоено» и «Теория + весь SQL» (`renderHome`, около 38). В боковой карточке чтение, понимание и SQL честно разделены (`masteryPanel`), и текст поясняет, что чтение не равно владению SQL.

`app.js`, `updateSideProgress` рассчитывает процент по выполненным обычным задачам, исключая экзамены и независимые проекты. Подпись «X из Y проверяемых SQL-задач» помогает понять знаменатель; процент нельзя трактовать как готовность академии или профессиональный уровень.

Подсказки не отмечаются в сохранённом прогрессе, попытки находятся в памяти (`state.attempts`), а imports могут содержать локальные отметки. Поэтому «самостоятельно освоено» и доля решений без помощи не измеряются. Это не мешает личному учебному прогрессу, но ограничивает заявления о компетенции и сертификации. Исторические зачёты корректно объяснены пользователю (`masteryPanel`).

Решение: согласовать подписи с фактическим критерием, различать выполнено/контроль пройден/повторено; если вводится метрика самостоятельности, сначала определить и сохранять её доказательства. Не повышать профессиональный уровень за чтение.

### UX-09. Поиск и полноценный справочник пока отсутствуют

**Средний продуктовый приоритет.** В `index.html` перечислено девять основных разделов. `views.js`, `renderRoute` (примерно 410–426) не содержит отдельного справочника или маршрута поиска; `renderPractice` предлагает только фильтр по модулю. Это подтверждённое отсутствие функции в прочитанных представлениях, а не неисправность существующего поиска.

При росте курса ручной просмотр карточек затруднит возврат к конкретной конструкции. Полезный следующий блок: поиск по заголовкам и концепциям + краткая справочная статья с PostgreSQL-примером и ссылками к уроку/практике. Не нужно рисовать поле поиска до реализации индексации и состояния «ничего не найдено».

### UX-10. Проблемы сохранения сообщаются только в консоль

**Средний приоритет.** В `progress.js`, `storeProgress` (49–53) ошибка localStorage логируется и функция возвращает объект; `loadProgress` (45–47) при повреждении данных возвращает пустой прогресс. `index.html` постоянно пишет «Прогресс в этом браузере». Пользователь без devtools не получает доказательства, что его работа действительно записана при отказе хранилища.

Импорт/экспорт уже реализованы и доступны в шапке; импорт требует явного подтверждения замены. Нужно показывать понятный persistent-статус при невозможности сохранения, предлагать экспорт и не обещать восстановление без успешной записи. Проверить через блокировку storage/квоту и повреждённый JSON. Отсутствие сетевой синхронизации обозначено честно.

## Сильные стороны, подтверждённые исходниками

- `html lang=ru`, landmarks main/nav/aside/header/footer, именованная основная навигация, контекстные хлебные ссылки и один главный заголовок у штатных представлений.
- Семантические ссылки для переходов и native buttons/textarea/details; код SQL не исполняется как разметка благодаря `esc`. Native textarea не создаёт ловушку Tab как некоторые редакторы.
- Подписи SQL-редактора, проекта и прогноза; ввод SQL выключает spellcheck, autocomplete и autocapitalize в основном редакторе; Ctrl/Cmd+Enter ограничен сфокусированным SQL-полем.
- Состояния неправильного/правильного ответа содержат текст, а не только цвет. SQL показывает различия результата, количество строк и предел отображения; NULL отличается визуально и текстом.
- Движок запускается отдельно от материалов, отображается статус, при отказе есть объяснение и кнопка повтора (`renderPage`). Ошибка SQL не заменяет весь учебный текст.
- Основной маршрут объясняет зависимости; урок показывает цель и предварительные темы, есть переход к следующему/предыдущему уроку и независимые контрольные.
- В проектах SQL-отчёты и аналитическая записка разделены. Прямо сказано, что выводы не оцениваются автоматически и защита не подтверждена без профессиональной проверки (`renderIndependentProject`).
- Планируемые направления помечены как находящиеся в разработке. Повторение честно сообщает, что автоматических уведомлений нет и пользователь должен вернуться сам.
- Есть светлая/тёмная темы, локальная копия прогресса, импорт/экспорт, responsive breakpoints, prefers-reduced-motion для CSS, фокус-visible и перенос длинных кнопок/части идентификаторов.

| Сценарий | Проверяемый результат |

| Только клавиатура | Skip-link, меню, импорт, схема, квиз, выбор задач, SQL, Check, таблица и возврат доступны; фокус виден и логичен |
| Скринридер | Названия полей/кнопок/выборов понятны, смена страницы и краткий итог SQL объявляются, таблица читается по заголовкам |
| Неверный → исправленный SQL | Ошибка не уничтожает черновик, сообщение доступно, верный результат даёт понятный зачёт |
| 320/360/768/1440px и 200%/400% zoom | Страница не требует горизонтальной прокрутки кроме двумерных таблиц/SQL; элементы не перекрывают друг друга |
| Длинная схема, длинный SQL, 0/80+ строк | Локальная прокрутка, ясный предел результата, доступные имена и возврат к условию |
| Обе темы и состояния | AA-контраст текста, иконок и фокуса, достаточный размер целей с учётом 2.5.8 и исключений |
| Отказ storage/движка/сети | Понятный статус, материалы доступны, возможны экспорт и повтор, нет ложного обещания сохранения |

Критерий завершения этого аудита: источники и ограничения документированы. Критерий готовности UX продукта шире: устранить приоритетные проблемы, подтвердить сценарии браузером и вспомогательными технологиями, затем провести наблюдение за реальными начинающими и опытными учащимися. Даже успешный axe не заменяет эти проверки.
