# Сборка и публикация

Изменения подготовлены для версии **0.11.0**.

## Подтверждённые недостатки исходного процесса

В исходном `95b4f3f4195588d8b45774140cf22e0b527508f5` job `deploy` зависел только от SQL-проверки `validate`. На push в main браузерные сценарии запускались **после** публикации; браузерная проверка локальной версии была только у pull request. В `upload-pages-artifact` стоял `path: .`, поэтому в пакет попадал весь checkout, включая тесты и документацию. `node_modules` в этом job не устанавливался, поэтому утверждать, что он уже публиковался, нельзя. Не было отдельной разрешающей выборки файлов, которая защищала бы от этого при дальнейшем изменении job.

В репозитории отсутствовал `package-lock.json`; CI явно использовал `--no-package-lock`. Прямые версии PGlite и Playwright были зафиксированы, но целостность и дерево транзитивных зависимостей не сохранялись. Браузер получал PGlite с внешнего CDN.

## Реализованные изменения

- `npm ci` устанавливает дерево из добавленного lockfile с проверкой integrity.
- `npm test` и `npm run test:unit` находят все `tests/*.test.mjs`, кроме отдельного браузерного сценария. Новые unit-тесты попадают в CI автоматически. Файлы исполняются последовательно, чтобы несколько WASM-баз не умножали пиковую память процесса проверки.
- `npm run build` создаёт `dist` с явным списком файлов приложения, `.nojekyll`, `release.json` и локальным PGlite из зафиксированной npm-зависимости. Тесты, документы, логи, `node_modules`, source maps и архивы расширений в публикацию не включены.
- `src/sql-worker.js` загружает `../vendor/pglite/index.js`. Отдельный внешний CDN больше не нужен для SQL. Дополнительные WASM/data-файлы разрешаются PGlite относительно своего локального URL.
- Одинаковый job для push и pull request выполняет SQL/unit-проверки, сборку и браузерные сценарии на содержимом `dist` до публикации.
- `npm run test:browser` последовательно запускает основной учебный сценарий `tests/browser.test.mjs` и интеграционный `tests/browser-runtime.mjs`. Второй проверяет ограничение времени тяжёлого запроса, восстановление SQL-среды после остановки и автоматический аудит доступности через закреплённый `@axe-core/playwright` 4.14.0. Это проверка сценариев и правил axe, а не исследование с реальными студентами или подтверждение полного соответствия WCAG.
- Pages публикует только уже проверенный artifact. Проверка настоящего публичного сайта остаётся после деплоя и дополнительно сверяет commit из `release.json` с `github.sha`.
- Права `pages: write` и `id-token: write` получает только job публикации.

## Локальная работа

```sh
npm ci
npm test
npm run build
npm run serve
# В другом терминале:
npm run test:browser
```

`npm run dev` объединяет сборку и запуск. Сервер по умолчанию слушает `127.0.0.1:4173`. После изменения исходников необходимо повторить сборку. Страницы исходного корня без сборки не включают каталог vendor и не являются проверяемой версией для публикации.

`release.json` содержит SHA из GitHub Actions; при локальной сборке используется `git rev-parse HEAD`, если доступен, иначе `null`. Локальная сборка сама по себе не означает публикацию. В сборку включены лицензия PGlite и его необходимые JS/WASM/data-файлы; PostgreSQL в браузере остаётся клиентской средой с ограничениями, описанными в `SQL_RUNTIME.md`.

## Ограничения проверки

Порядок job и локальная сборка проверяются в рабочем окружении. Успех нового GitHub Actions workflow и публикация считаются подтверждёнными только после реального запуска и проверки release.json. Постпубликационный тест сообщает о регрессии, но не откатывает сайт автоматически. Производительность доставки WASM при медленной мобильной сети требует отдельного замера. Внешняя загрузка необязательных шрифтов из исходного HTML рассматривается отдельно; она не нужна для запуска SQL.
